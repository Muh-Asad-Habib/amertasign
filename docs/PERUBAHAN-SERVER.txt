1. KEAMANAN RESET PASSWORD  (TANPA OTP / EMAIL — keputusan terbaru)
================================================================
KEPUTUSAN TIM MOBILE: reset password TIDAK memakai OTP dan TIDAK
mengirim email apa pun. Layanan kirim email berbayar dan menambah
kerumitan, sementara aplikasi masih tahap prototipe.
- JANGAN membuat endpoint /auth/password-reset/request|verify|confirm.
- Kalau alur OTP terlanjur dikerjakan sebagian, nonaktifkan saja —
  mobile tidak akan memakainya.

Alur yang dipakai mobile (SUDAH ADA — pertahankan, jangan diubah):
  POST /auth/forgot-password
  body: { "username": "...", "email": "...", "newPassword": "..." }
  - Password diganti bila kombinasi username + email cocok dengan
    akun terdaftar.

Yang diminta hanya pengaman ringan (gratis, tanpa layanan luar):
  a) Rate limit: maks 5 percobaan / jam (per IP dan per username).
     Lebih dari itu balas 429 + code RATE_LIMITED (selaras poin 19).
  b) Bila kombinasi tidak cocok, balas SATU pesan error generik
     (mis. "Username atau email tidak cocok") — jangan sebut bagian
     mana yang salah, jangan bocorkan akun ada/tidak.
  c) Setelah password berhasil diganti, revoke SEMUA refresh token /
     sesi lama milik user tersebut.
  d) Validasi newPassword memakai aturan yang sama dengan register.
  e) Jangan pernah menulis password ke log (lihat poin 12).

Catatan: kami paham alur ini lebih lemah daripada OTP/email — ini
keputusan sadar untuk fase prototipe. Bila nanti dirilis publik,
alur OTP bisa dipertimbangkan ulang.

2. KEBIJAKAN AKSES MODE TAMU  (WAJIB DIIKUTI)
================================================================
Aplikasi punya MODE TAMU (tanpa akun). Aturannya:

  MODE TAMU BOLEH MEMAKAI SEMUA FITUR, KECUALI RIWAYAT TERJEMAHAN.

Matriks akses yang harus berlaku di server:

  Endpoint                              Tamu (tanpa token)   Login
  ------------------------------------  -------------------  --------
  POST /translate/sign-to-text          BOLEH                Boleh
  POST /translate/text-to-sign          BOLEH                Boleh
  GET  /dictionary                      BOLEH                Boleh
  GET  /dictionary?search=...           BOLEH                Boleh
  GET  /dictionary/{id}                 BOLEH                Boleh
  GET/POST/DELETE /history              TIDAK (butuh token)  Boleh
  GET/PUT/DELETE /favorites             TIDAK (butuh token)  Boleh
  GET  /auth/me, PATCH /users/me        TIDAK (butuh token)  Boleh

Penjelasan tambahan:
- Favorit mode tamu DISIMPAN DI PERANGKAT (lokal), jadi server tidak
  perlu menyediakan endpoint favorit untuk tamu. Aplikasi tidak akan
  memanggil /favorites saat mode tamu.
- Riwayat mode tamu memang tidak disimpan sama sekali. Aplikasi tidak
  akan memanggil /history saat mode tamu.

Yang WAJIB dipastikan di server:
  a) Endpoint /translate/* dan /dictionary/* JANGAN mewajibkan JWT.
     Request tanpa header Authorization harus tetap diproses normal,
     bukan dibalas 401.
  b) Aplikasi mobile SUDAH mengirim "Authorization: Bearer <token>"
     pada upload ke /translate/sign-to-text bila pengguna login.
     Adanya token TIDAK BOLEH membuat request ditolak. Idealnya
     token divalidasi (untuk pencatatan/kuota), minimal diabaikan.
  c) Karena /translate/* terbuka untuk tamu, WAJIB ada rate limit
     per IP / per perangkat supaya endpoint AI tidak bebas dipakai
     pihak luar. Besaran limit: lihat poin 7 (sudah diperbarui
     mengikuti mode multi-isyarat).
  d) Untuk endpoint yang memang butuh token (/history, /favorites,
     /auth/me, /users/me): bila token tidak ada atau tidak valid,
     balas HTTP 401 dengan error.code "UNAUTHORIZED" dan body JSON.
     (Mobile otomatis refresh token lalu mengulang request 1x.)

3. VALIDASI & BATASAN UPLOAD
================================================================
- Batasi MIME type: video/mp4, image/jpeg, image/png.
- Batasi ukuran file maksimum (usul 25-50 MB).
- Batasi durasi video maksimum (usul <= 15 detik — sama dengan
  batas rekaman di aplikasi).
- Batasi waktu pemrosesan AI (timeout), jangan menggantung.
- Saat menolak, balas dengan error code yang stabil (lihat bagian 4).


================================================================
4. DAFTAR ERROR CODE YANG WAJIB DIPAKAI
================================================================
Mobile memetakan code berikut menjadi kalimat Bahasa Indonesia yang
ramah pengguna. Mohon pakai PERSIS code ini (huruf besar + garis bawah):

  UNAUTHORIZED          -> sesi berakhir, minta login ulang
  FORBIDDEN             -> tidak punya akses
  FILE_TOO_LARGE        -> berkas terlalu besar
  UNSUPPORTED_MEDIA     -> format media tidak didukung
  PROCESSING_TIMEOUT    -> analisis AI kelamaan
  AI_PROCESSING_FAILED  -> isyarat gagal dianalisis
  UPLOAD_ERROR          -> unggah gagal (umum)
  RATE_LIMITED          -> terlalu banyak permintaan (lihat poin 19)
  TEXT_TOO_LONG         -> teks > 200 karakter (lihat poin 18)
  TEXT_EMPTY            -> teks kosong (lihat poin 18)

Aturan tambahan:
- Kalau code tidak dikenali, mobile menampilkan error.message apa
  adanya. Karena itu error.message harus selalu Bahasa Indonesia dan
  layak dibaca pengguna awam (jangan stack trace / pesan teknis).
- HTTP 401 / 403 / 413 / 5xx tetap ditangani meski code tidak dikenal,
  tapi lebih baik code-nya tetap dikirim.


================================================================
5. SEMUA ERROR HARUS BERBENTUK JSON — TERMASUK ERROR GATEWAY
================================================================
Mobile selalu membaca body respons sebagai JSON:
  { "success": false, "error": { "code": "...", "message": "..." } }

Yang sering lolos jadi HTML dan membuat pesan error jadi jelek:
  - 413 Request Entity Too Large dari nginx (bukan dari aplikasi)
  - 502 / 504 dari gateway saat backend AI lambat
  - 429 dari rate limiter di gateway
  - halaman error default framework

Mohon konfigurasikan agar kasus di atas tetap membalas JSON.


================================================================
6. TIMEOUT & BATAS UKURAN DI NGINX / REVERSE PROXY
================================================================
Batas waktu yang dipakai mobile:
  - Request JSON biasa (login, kamus, riwayat) : 15 detik
  - Upload GAMBAR ke /translate/sign-to-text   : 60 detik
  - Upload VIDEO  ke /translate/sign-to-text   : 120 detik

Supaya gateway tidak memutus lebih dulu:
  proxy_read_timeout      >= 180s
  proxy_send_timeout      >= 180s
  client_body_timeout     >= 180s
  client_max_body_size    >= ukuran video maksimum (usul 50m)

Kalau gateway memutus duluan, pengguna melihat error jaringan padahal
AI masih memproses.


================================================================
7. POLA REQUEST AI DARI MOBILE — SUDAH BERUBAH, MOHON DIBACA ULANG
================================================================
SEBELUMNYA: 1 rekaman = 2 request paralel (stage=abjad + stage=kata).

SEKARANG (mulai versi aplikasi berikutnya): untuk mendukung deteksi
RANGKAIAN isyarat (lihat poin 14), 1 rekaman menjadi:
  - 1 request  stage=kata   (video penuh, MP4)
  - s.d. 12 request stage=abjad (frame JPEG diambil dari video,
    dikirim bertahap maksimal 3 request bersamaan)
  Total: s.d. 13 request per satu kali terjemahan, selesai dalam
  beberapa detik (burst singkat).

TAMBAHAN: pengguna kini bisa MENGUNCI jenis isyarat di layar kamera
(Otomatis / Huruf / Angka / Kata). Beban per terjemahan mengikuti mode:

  Otomatis : s.d. 13 request  (1 kata + s.d. 12 abjad) — kasus terburuk
  Huruf    : s.d. 12 request  (abjad saja, TANPA request video)
  Angka    : 1 request        (stage=kata saja)
  Kata     : 1 request        (stage=kata saja)

Jadi angka 13 di atas tetap batas atas yang harus ditanggung server,
tapi dalam pemakaian nyata sebagian besar terjemahan akan jauh lebih
ringan. Tidak ada nilai stage baru — mode hanya memilih stage yang
sudah ada dan menyaring "candidates[]" di sisi aplikasi.

Yang perlu dipastikan:
- Rate limit JANGAN memblokir burst ini:
    login : minimal 30 request / menit / user
    tamu  : minimal 30 request / menit / IP
  (Burst 13 request + jeda antar percobaan; 30/menit aman.)
- POLA BOROS INI SEMENTARA. Begitu poin 14 (stage=auto multi) siap,
  mobile kembali ke 1 REQUEST per terjemahan dan limit bisa
  diturunkan lagi. Ini alasan kuat memprioritaskan poin 14.
- Server sanggup memproses beberapa request abjad secara paralel
  (frame JPEG kecil, model gambar — seharusnya ringan).
- Nama field multipart dari mobile: "file" (berkas) dan "stage".
  Mohon konfirmasi ini sesuai dengan yang server harapkan.
- Mobile sengaja tidak menyetel Content-Type manual supaya boundary
  multipart dibuat otomatis. Parser server membaca boundary dari
  header request seperti biasa.

8. RIWAYAT TERJEMAHAN — /history
================================================================
a) DELETE /history harus IDEMPOTEN.
   Mobile punya fitur hapus dengan tombol "Urungkan": riwayat langsung
   hilang di layar, tapi DELETE baru dikirim setelah 5 detik bila
   pengguna tidak mengurungkan.
   - DELETE saat riwayat sudah kosong harus balas 200, JANGAN 404.
   - Aman bila DELETE terkirim lebih dari sekali.
   - Catatan: bila pengguna logout saat masih dalam jeda 5 detik,
     aplikasi mengirim DELETE tersebut SEBELUM POST /auth/logout —
     urutan request ini normal, bukan anomali.

b) GET /history harus mendukung parameter "kind".
   Saat aplikasi dibuka, mobile memanggil 2 request paralel:
     GET /history?limit=10&kind=isyarat-ke-teks
     GET /history?limit=10&kind=teks-ke-isyarat
   Nilai "kind" persis seperti di atas (huruf kecil, pakai tanda hubung).
   Response tetap: { "success": true, "data": { "items": [...] } }
   (Mobile kini tahan gagal parsial: satu request gagal, satunya
   tetap ditampilkan.)

c) POST /history membalas:
     { "item": { id, kind, text, signLanguageType, createdAt } }
   Mobile menampilkan item sementara lebih dulu, lalu menggantinya
   dengan item resmi dari server ini.


================================================================
9. KAMUS — /dictionary
================================================================
a) Paginasi cursor. Mobile memanggil:
     GET /dictionary?limit=100
     GET /dictionary?limit=100&cursor=<nextCursor>   (berulang)
   sampai nextCursor bernilai null.
   - Urutan hasil harus STABIL antar halaman (mis. urut id / createdAt)
     supaya tidak ada entri dobel atau terlewat.
   - nextCursor harus null (bukan string kosong) di halaman terakhir.

b) Pencarian:
     GET /dictionary?search=<kata>&limit=10
   Harus tidak case-sensitive dan cocok pada sebagian kata (substring),
   karena dipakai untuk saran pencarian saat pengguna mengetik.

c) imageUrl / videoUrl boleh berupa path relatif (mis. "/media/abc.mp4")
   karena mobile otomatis menggabungkan dengan base URL. Yang penting
   KONSISTEN, jangan campur relatif dan absolut.

d) Mobile menyimpan kamus di cache selama 30 MENIT (dan kini ada
   pull-to-refresh yang memaksa ambil ulang). Kalau data kamus
   diubah di server, perangkat bisa masih menampilkan data lama
   sampai 30 menit. Mohon kabari kami bila ada perubahan data kamus.
   (Opsional: kirim header ETag / Last-Modified, atau tambahkan field
   "version" pada response kamus, supaya mobile bisa invalidate cache
   lebih pintar.)

e) Pastikan data kamus lengkap dan seluruh imageUrl / videoUrl valid
   serta bisa diakses dari perangkat (bukan hanya dari jaringan lokal).

14. MODE MULTI-ISYARAT: stage=auto + SEGMENTASI  << INTI PRODUK >>
================================================================
INI PERMINTAAN TERPENTING DI SELURUH DOKUMEN.

Tujuan produk: pengguna memperagakan BEBERAPA isyarat berurutan
dalam SATU rekaman (mis. "S-A-Y-A" lalu isyarat "MAKAN"), dan
aplikasi menghasilkan teks lengkap "SAYA MAKAN" — bukan cuma satu
huruf/angka/kata seperti sekarang.

Kondisi sekarang di server:
  - stage=abjad : 1 gambar  -> 1 label huruf
  - stage=kata  : 1 video   -> 1 label kata/angka (SELURUH video
                  dianggap SATU isyarat, tidak ada segmentasi)

Solusi sementara di mobile (SUDAH kami terapkan, lihat poin 7):
  mobile mengambil banyak frame dari video lalu menembak stage=abjad
  berkali-kali untuk merangkai EJAAN huruf/angka. Tapi cara ini:
  - boros (s.d. 13 request per terjemahan),
  - TIDAK BISA mendeteksi beberapa KATA dinamis dalam satu video
    (memotong video jadi segmen tidak mungkin dilakukan di aplikasi).
  Jadi rangkaian multi-KATA hanya bisa diwujudkan DI SERVER.

YANG DIMINTA — tahap demi tahap:

  TAHAP A (dasar): stage = "auto"
    POST /api/v1/translate/sign-to-text, field stage = "auto",
    file = video MP4.
    Server menjalankan kedua model terhadap video dan membalas
    kandidat terbaik — bentuk response SAMA seperti sekarang:
      { text, confidence, candidates[], mode, stage, model_loaded,
        note }
    ("stage" pada response diisi stage pemenang: "abjad"/"kata".)
    Spesifikasi rinci + pseudocode sudah ada di berkas
    docs/BACKEND-AUTO-DETECT.txt di repo mobile — masih berlaku.

  TAHAP B (inti produk): segmentasi temporal
    Masih endpoint & field yang sama (stage="auto"), server:
    1) Deteksi landmark tangan per frame (MediaPipe — sudah dipakai
       server saat ini).
    2) Segmentasi waktu: pisahkan "momen menahan isyarat" dari
       "gerak transisi antar isyarat" (mis. energi gerak landmark
       rendah = sedang menahan; tinggi = transisi).
    3) Klasifikasikan TIAP segmen (model abjad untuk pose statis,
       model kata untuk segmen dinamis).
    4) Rangkai hasil: huruf berurutan digabung jadi ejaan kata
       ("S","A","Y","A" -> "SAYA"), token kata berdiri sendiri,
       pisahkan antar token dengan spasi.

    Response yang diharapkan mobile (perluasan KOMPATIBEL — field
    lama tetap ada, field baru "segments" ditambahkan):
      {
        "text": "SAYA MAKAN",
        "confidence": 0.87,          // rata-rata / minimum segmen
        "candidates": [...],         // kandidat teks utuh (opsional)
        "mode": "BISINDO",
        "stage": "auto",
        "model_loaded": true,
        "note": null,
        "segments": [
          { "startMs": 300,  "endMs": 1100, "label": "S",
            "kind": "huruf", "confidence": 0.93, "candidates": [...] },
          { "startMs": 1400, "endMs": 2100, "label": "A",
            "kind": "huruf", "confidence": 0.91, "candidates": [...] },
          ...
          { "startMs": 5200, "endMs": 7400, "label": "MAKAN",
            "kind": "kata",  "confidence": 0.82, "candidates": [...] }
        ]
      }
    - "kind" per segmen: "huruf" | "angka" | "kata".
    - Segmen yang tidak dikenali boleh dilewati (jangan dikirim
      dengan label kosong) atau diberi note.
    - Kalau hanya 1 isyarat terdeteksi, "segments" berisi 1 item —
      mobile tetap menampilkan dengan benar.

  KOMPATIBILITAS MUNDUR (WAJIB):
    - stage="abjad" dan stage="kata" yang lama TIDAK BOLEH berubah
      perilakunya — versi aplikasi yang sudah beredar memakainya.
    - stage="auto" adalah nilai BARU; kalau belum siap, balas error
      JSON code "UNSUPPORTED_STAGE" (mobile akan fallback otomatis
      ke pola lama).

  SETELAH TAHAP B SIAP:
    - Mobile beralih ke 1 request stage=auto per terjemahan.
    - Beban server turun drastis dibanding pola poin 7.
    - Mohon kabari tim mobile begitu bisa diuji di produksi.

15. HAPUS RIWAYAT PER ITEM — DELETE /history/{id}
================================================================
Sekarang server hanya punya DELETE /history (hapus SEMUA).
Pengguna tidak bisa menghapus satu entri riwayat saja.

Permintaan:
  DELETE /api/v1/history/{id}   (butuh Bearer token)
  - Hanya boleh menghapus item milik user pemilik token
    (cek kepemilikan, bukan hanya keberadaan id).
  - Balas { "success": true, "data": { "deleted": true } }.
  - IDEMPOTEN: id yang sudah tidak ada balas 200 dengan
    deleted: false (JANGAN 404), karena mobile memakai pola
    "hapus dulu di layar + tombol Urungkan" seperti DELETE massal.

Catatan: UI hapus per item di mobile SENGAJA belum kami aktifkan
supaya tidak ada tombol yang gagal. Begitu endpoint ini siap dan
dikonfirmasi, kami aktifkan.

OPSIONAL (nice to have, bukan syarat):
  GET /history tanpa parameter "kind" yang membalas gabungan
  { "items": [...] } berisi kedua arah sekaligus (tetap maksimal
  10 per arah), supaya pembukaan aplikasi cukup 1 request, bukan 2.
  Pola 2 request dengan "kind" (poin 8b) tetap harus jalan untuk
  kompatibilitas versi aplikasi yang sudah beredar.

16. SINKRONISASI PREFERENSI PENGGUNA ANTAR PERANGKAT
================================================================
Preferensi berikut saat ini HANYA tersimpan di perangkat
(SecureStore lokal): gender avatar peraga, kecepatan isyarat,
gender suara TTS, kecepatan bicara TTS, mode tema, simpan riwayat
on/off. Kalau pengguna ganti HP atau reinstall, semua hilang.

Permintaan (prioritas menengah, bukan pemblokir rilis):
  GET  /api/v1/users/me/settings   (butuh token)
    -> { "settings": { ...objek JSON bebas... } }
  PUT  /api/v1/users/me/settings   (butuh token)
    body: { "settings": { ...objek JSON penuh (replace)... } }
    -> { "settings": { ... } }

  - Cukup simpan sebagai satu kolom JSON per user; server TIDAK
    perlu memvalidasi isi tiap field (skema dikelola mobile, akan
    bertambah seiring fitur). Batasi ukuran payload (usul <= 8 KB).
  - Mode tamu tidak memanggil endpoint ini.


================================================================
17. KONFIRMASI KONTRAK /auth/refresh  (penting, cek saja)
================================================================
Mobile memakai kontrak ini (mohon KONFIRMASI, bukan ubah):
  POST /api/v1/auth/refresh
  body    : { "refreshToken": "..." }
  sukses  : { "success": true, "data": { "accessToken": "..." } }
  gagal   : HTTP 401 + { success: false, error: {...} }

Dua hal yang harus dipastikan:
  a) Mobile HANYA membaca data.accessToken dari response refresh.
     Kalau server melakukan ROTASI refresh token (refresh token lama
     hangus setiap dipakai), mobile akan ter-logout diam-diam saat
     refresh berikutnya. Jadi: refresh token JANGAN dirotasi diam-
     diam. Kalau tim server ingin rotasi, kabari kami dulu — kami
     tambahkan dukungan membaca data.refreshToken baru, baru rotasi
     boleh diaktifkan.
  b) Refresh token yang sudah kedaluwarsa/di-revoke harus balas 401
     JSON (bukan 500 / HTML), supaya mobile bisa mengarahkan
     pengguna login ulang dengan pesan yang benar.

18. BATAS PANJANG TEKS /translate/text-to-sign
================================================================
Mobile kini MEMBATASI input maksimal 200 KARAKTER (huruf yang
diketik, transkrip suara, dan teks kiriman dari riwayat semuanya
dipotong di 200).

Permintaan:
  - Validasi juga di server: teks > 200 karakter ditolak dengan
    HTTP 422 dan error code "TEXT_TOO_LONG",
    message contoh: "Teks maksimal 200 karakter."
  - Teks kosong / hanya spasi: HTTP 422, code "TEXT_EMPTY".
  - Jangan memproses AI/kamus untuk input yang gagal validasi.

(Kedua code sudah masuk daftar poin 4.)

19. FORMAT RESPONSE RATE LIMIT — HTTP 429
================================================================
Poin 2c dan 7 meminta rate limit. Yang belum disepakati adalah
BENTUK responsnya saat limit tercapai.

Permintaan:
  HTTP 429 + body JSON:
  { "success": false,
    "error": { "code": "RATE_LIMITED",
               "message": "Terlalu banyak permintaan. Coba lagi
                           dalam beberapa saat." } }
  - Sertakan juga header Retry-After (detik) bila memungkinkan.
  - PENTING: 429 dari nginx/gateway juga harus JSON seperti ini,
    jangan HTML (sejalan dengan poin 5).
  - Message harus Bahasa Indonesia — mobile menampilkannya
    apa adanya bila code belum dikenali.

20. KONFIRMASI KONTRAK LOGIN GOOGLE + FIELD hasPassword
================================================================
Dua kontrak yang SUDAH dipakai mobile — mohon dicek masih sesuai
dan JANGAN diubah tanpa kabar:

a) Alur web Google OAuth:
   GET /api/v1/auth/google/start?returnUrl=<url>
   - Sukses: server redirect ke returnUrl dengan query
       ?accessToken=<jwt>&refreshToken=<jwt>
   - Gagal / dibatalkan: redirect ke returnUrl dengan query
       ?error=<KODE>&message=<pesan>
     Khusus pembatalan oleh pengguna, kirim error=CANCELLED —
     mobile sengaja TIDAK menampilkan pesan apa pun untuk kode ini.
     Kode selain CANCELLED akan ditampilkan ke pengguna lewat
     message (Bahasa Indonesia).
   - Nama parameter harus persis: accessToken, refreshToken,
     error, message (camelCase).

b) Field "hasPassword" pada objek user:
   Response GET /auth/me dan PATCH /users/me harus menyertakan
   user.hasPassword (boolean):
     - false untuk akun yang dibuat via Google (tidak punya password)
     - true untuk akun username+password
   Mobile memakainya untuk MENYEMBUNYIKAN menu "Ganti Password"
   pada akun Google. Kalau field ini tidak ada, semua akun dianggap
   punya password dan pengguna Google melihat form yang pasti gagal.
