CARA MEMAKAI DOKUMEN INI  —  BACA DULU SEBELUM MENGUBAH APA PUN
================================================================
PENTING: JANGAN langsung menerapkan semua poin di bawah tanpa
pengecekan. Termasuk bila pengerjaan dibantu AI — AI TIDAK BOLEH
langsung menulis ulang kode berdasarkan dokumen ini saja.

Urutannya WAJIB begini untuk SETIAP poin (bagian 1 sampai 13):

  LANGKAH 1 — CEK KONDISI SEKARANG
    Buka kode / konfigurasi yang bersangkutan dan pastikan dulu:
    - Apakah perilaku yang diminta SUDAH ada? Kalau sudah sesuai,
      LEWATI poin itu, jangan diubah. Cukup balas "sudah sesuai".
    - Kalau belum ada, catat di mana persisnya perlu diubah.

  LANGKAH 2 — NILAI DAMPAKNYA
    - Apakah perubahan ini merusak endpoint lain yang sudah jalan?
    - Apakah ada klien/layanan lain yang ikut terpengaruh?
    - Kalau ada risiko, JANGAN dieksekusi. Tanyakan dulu ke tim mobile.

  LANGKAH 3 — BARU UBAH, SATU POIN SATU KALI
    - Kerjakan bertahap, jangan borongan dalam satu commit besar.
    - Jangan mengubah bentuk response yang sudah dipakai mobile
      (lihat "Aturan dasar" di bawah) kecuali diminta eksplisit.

  LANGKAH 4 — UJI SEBELUM DIANGGAP SELESAI
    - Uji endpoint yang diubah (minimal lewat curl/Postman):
      kasus normal, kasus gagal, dan kasus tanpa token.
    - Pastikan endpoint LAIN yang tidak disentuh masih normal.

  LANGKAH 5 — LAPORKAN
    Balas ke tim mobile per poin dengan status:
      "sudah sesuai" / "sudah diubah" / "belum dikerjakan" /
      "tidak bisa, alasannya ..."

ATURAN KERAS:
- Jangan menghapus atau mengganti nama endpoint yang sudah dipakai
  aplikasi mobile tanpa memberi tahu tim mobile lebih dulu.
- Jangan mengubah format response { success, data } / { success, error }.
- Kalau ada poin di dokumen ini yang terasa keliru atau bertentangan
  dengan kondisi server sebenarnya, JANGAN dipaksakan. Tanyakan dulu.
- Kalau ragu pada satu poin, lewati poin itu dan tandai sebagai
  "perlu diskusi", jangan menebak.

Kalau semua sudah dicek dan aman, silakan lanjutkan pengerjaan.

ATURAN DASAR (SUDAH DIPAKAI MOBILE — MOHON JANGAN DIUBAH)
================================================================
- Sukses : { "success": true, "data": ... }
- Gagal  : { "success": false, "error": { "code": "...", "message": "..." } }
- Auth   : Bearer JWT di header Authorization
           Refresh: POST /api/v1/auth/refresh { "refreshToken": "..." }
- Base URL: https://amertasign.lab-if.tech/api/v1


================================================================
1. KEAMANAN RESET PASSWORD  (paling penting)
================================================================
Masalah:
  POST /auth/forgot-password sekarang menerima
  { username, email, newPassword } dan langsung mengganti password
  hanya dengan mencocokkan username + email.
  Siapa pun yang tahu username + email seseorang bisa membajak akun.

Ganti menjadi 3 tahap:
  1) POST /auth/password-reset/request
     body: { "identifier": "<username atau email>" }
     - Kirim OTP 6 digit / link sekali pakai ke email terdaftar.
     - SELALU balas sukses generik (jangan bocorkan akun ada/tidak).
     - Rate limit: 1 permintaan / 60 detik, maks 5 / jam
       (per identifier dan per IP).
  2) POST /auth/password-reset/verify
     body: { "identifier": "...", "otp": "123456" }
     - Balas resetToken sementara (sekali pakai, umur pendek).
     - Maks 5 percobaan salah, lalu blokir sementara.
  3) POST /auth/password-reset/confirm
     body: { "resetToken": "...", "newPassword": "..." }
     - Token disimpan sebagai hash, expire <= 15 menit, sekali pakai.
     - Setelah password diganti, revoke SEMUA refresh token / sesi
       lama milik user tersebut.

Catatan: OTP dan reset token disimpan dalam bentuk hash.
Jangan pernah menulis OTP / password ke log.


================================================================
2. KEBIJAKAN AKSES MODE TAMU  (WAJIB DIIKUTI)
================================================================
Aplikasi punya MODE TAMU (tanpa akun). Aturannya:

  MODE TAMU BOLEH MEMAKAI SEMUA FITUR, KECUALI RIWAYAT TERJEMAHAN.

Matriks akses yang harus berlaku di server:

  Endpoint                              Tamu (tanpa token)   Login
  ------------------------------------  -------------------  --------
  POST /translate/sign-to-text          BOLEH                Boleh
  POST /translate/text-to-sign          BOLEH                Boleh
  GET  /dictionary                      BOLEH                Boleh
  GET  /dictionary?search=...           BOLEH                Boleh
  GET  /dictionary/{id}                 BOLEH                Boleh
  GET/POST/DELETE /history              TIDAK (butuh token)  Boleh
  GET/PUT/DELETE /favorites             TIDAK (butuh token)  Boleh
  GET  /auth/me, PATCH /users/me        TIDAK (butuh token)  Boleh

Penjelasan tambahan:
- Favorit mode tamu DISIMPAN DI PERANGKAT (lokal), jadi server tidak
  perlu menyediakan endpoint favorit untuk tamu. Aplikasi tidak akan
  memanggil /favorites saat mode tamu.
- Riwayat mode tamu memang tidak disimpan sama sekali. Aplikasi tidak
  akan memanggil /history saat mode tamu.

Yang WAJIB dipastikan di server:
  a) Endpoint /translate/* dan /dictionary/* JANGAN mewajibkan JWT.
     Request tanpa header Authorization harus tetap diproses normal,
     bukan dibalas 401.
  b) Aplikasi mobile SUDAH mengirim "Authorization: Bearer <token>"
     pada upload ke /translate/sign-to-text bila pengguna login.
     Adanya token TIDAK BOLEH membuat request ditolak. Idealnya
     token divalidasi (untuk pencatatan/kuota), minimal diabaikan.
  c) Karena /translate/* terbuka untuk tamu, WAJIB ada rate limit
     per IP / per perangkat supaya endpoint AI tidak bebas dipakai
     pihak luar. Usul: 10-20 request per menit per IP.
     (Lihat juga bagian 7: satu rekaman = 2 request paralel.)
  d) Untuk endpoint yang memang butuh token (/history, /favorites,
     /auth/me, /users/me): bila token tidak ada atau tidak valid,
     balas HTTP 401 dengan error.code "UNAUTHORIZED" dan body JSON.
     (Mobile otomatis refresh token lalu mengulang request 1x.)


================================================================
3. VALIDASI & BATASAN UPLOAD
================================================================
- Batasi MIME type: video/mp4, image/jpeg, image/png.
- Batasi ukuran file maksimum (usul 25-50 MB).
- Batasi durasi video maksimum (usul <= 15 detik).
- Batasi waktu pemrosesan AI (timeout), jangan menggantung.
- Saat menolak, balas dengan error code yang stabil (lihat bagian 4).


================================================================
4. DAFTAR ERROR CODE YANG WAJIB DIPAKAI
================================================================
Mobile memetakan code berikut menjadi kalimat Bahasa Indonesia yang
ramah pengguna. Mohon pakai PERSIS code ini (huruf besar + garis bawah):

  UNAUTHORIZED          -> sesi berakhir, minta login ulang
  FORBIDDEN             -> tidak punya akses
  FILE_TOO_LARGE        -> berkas terlalu besar
  UNSUPPORTED_MEDIA     -> format media tidak didukung
  PROCESSING_TIMEOUT    -> analisis AI kelamaan
  AI_PROCESSING_FAILED  -> isyarat gagal dianalisis
  UPLOAD_ERROR          -> unggah gagal (umum)

Aturan tambahan:
- Kalau code tidak dikenali, mobile menampilkan error.message apa
  adanya. Karena itu error.message harus selalu Bahasa Indonesia dan
  layak dibaca pengguna awam (jangan stack trace / pesan teknis).
- HTTP 401 / 403 / 413 / 5xx tetap ditangani meski code tidak dikenal,
  tapi lebih baik code-nya tetap dikirim.


================================================================
5. SEMUA ERROR HARUS BERBENTUK JSON — TERMASUK ERROR GATEWAY
================================================================
Mobile selalu membaca body respons sebagai JSON:
  { "success": false, "error": { "code": "...", "message": "..." } }

Yang sering lolos jadi HTML dan membuat pesan error jadi jelek:
  - 413 Request Entity Too Large dari nginx (bukan dari aplikasi)
  - 502 / 504 dari gateway saat backend AI lambat
  - halaman error default framework

Mohon konfigurasikan agar kasus di atas tetap membalas JSON.


================================================================
6. TIMEOUT & BATAS UKURAN DI NGINX / REVERSE PROXY
================================================================
Batas waktu yang dipakai mobile:
  - Request JSON biasa (login, kamus, riwayat) : 15 detik
  - Upload GAMBAR ke /translate/sign-to-text   : 60 detik
  - Upload VIDEO  ke /translate/sign-to-text   : 120 detik

Supaya gateway tidak memutus lebih dulu:
  proxy_read_timeout      >= 180s
  proxy_send_timeout      >= 180s
  client_body_timeout     >= 180s
  client_max_body_size    >= ukuran video maksimum (usul 50m)

Kalau gateway memutus duluan, pengguna melihat error jaringan padahal
AI masih memproses.


================================================================
7. ENDPOINT AI DIPANGGIL DUA KALI PARALEL UNTUK SATU REKAMAN
================================================================
Fitur deteksi otomatis mengirim 1 rekaman sebagai 2 request bersamaan
ke POST /translate/sign-to-text:
  - field "stage" = "abjad"  -> 1 frame gambar JPEG
  - field "stage" = "kata"   -> video MP4
Mobile lalu memilih kandidat dengan confidence tertinggi.

Yang perlu dipastikan:
- Rate limit tidak memblokir 2 request berturut-turut dari pengguna
  yang sama (usul: minimal 10 request / menit / user untuk yang login,
  dan 10-20 request / menit / IP untuk mode tamu).
- Server sanggup memproses keduanya secara paralel.
- Nama field multipart dari mobile: "file" (berkas) dan "stage".
  Mohon konfirmasi ini sesuai dengan yang server harapkan.
- Mobile sengaja tidak menyetel Content-Type manual supaya boundary
  multipart dibuat otomatis. Parser server membaca boundary dari
  header request seperti biasa.


================================================================
8. RIWAYAT TERJEMAHAN — /history
================================================================
a) DELETE /history harus IDEMPOTEN.
   Mobile punya fitur hapus dengan tombol "Urungkan": riwayat langsung
   hilang di layar, tapi DELETE baru dikirim setelah 5 detik bila
   pengguna tidak mengurungkan.
   - DELETE saat riwayat sudah kosong harus balas 200, JANGAN 404.
   - Aman bila DELETE terkirim lebih dari sekali.

b) GET /history harus mendukung parameter "kind".
   Saat aplikasi dibuka, mobile memanggil 2 request paralel:
     GET /history?limit=10&kind=isyarat-ke-teks
     GET /history?limit=10&kind=teks-ke-isyarat
   Nilai "kind" persis seperti di atas (huruf kecil, pakai tanda hubung).
   Response tetap: { "success": true, "data": { "items": [...] } }

c) POST /history membalas:
     { "item": { id, kind, text, signLanguageType, createdAt } }
   Mobile menampilkan item sementara lebih dulu, lalu menggantinya
   dengan item resmi dari server ini.


================================================================
9. KAMUS — /dictionary
================================================================
a) Paginasi cursor. Mobile memanggil:
     GET /dictionary?limit=100
     GET /dictionary?limit=100&cursor=<nextCursor>   (berulang)
   sampai nextCursor bernilai null.
   - Urutan hasil harus STABIL antar halaman (mis. urut id / createdAt)
     supaya tidak ada entri dobel atau terlewat.
   - nextCursor harus null (bukan string kosong) di halaman terakhir.

b) Pencarian:
     GET /dictionary?search=<kata>&limit=10
   Harus tidak case-sensitive dan cocok pada sebagian kata (substring),
   karena dipakai untuk saran pencarian saat pengguna mengetik.

c) imageUrl / videoUrl boleh berupa path relatif (mis. "/media/abc.mp4")
   karena mobile otomatis menggabungkan dengan base URL. Yang penting
   KONSISTEN, jangan campur relatif dan absolut.

d) Mobile menyimpan kamus di cache selama 30 MENIT. Kalau data kamus
   diubah di server, perangkat bisa masih menampilkan data lama sampai
   30 menit atau sampai aplikasi dibuka ulang. Mohon kabari kami bila
   ada perubahan data kamus.
   (Opsional: kirim header ETag / Last-Modified, atau tambahkan field
   "version" pada response kamus, supaya mobile bisa invalidate cache
   lebih pintar.)

e) Pastikan data kamus lengkap dan seluruh imageUrl / videoUrl valid
   serta bisa diakses dari perangkat (bukan hanya dari jaringan lokal).


================================================================
10. UPLOAD AVATAR (PROFIL)
================================================================
- Sekarang mobile mengirim avatar sebagai string base64 di dalam JSON
  PATCH /users/me. Payload jadi besar dan rawan timeout.
- Usulan: sediakan PATCH /users/me/avatar dengan multipart/form-data,
  field "avatar".
  - Validasi tipe dan ukuran berkas.
  - Simpan ke storage/disk.
  - Balas { user } dengan avatarUrl berupa URL atau path relatif.


================================================================
11. HAPUS AKUN
================================================================
- DELETE /users/me (butuh auth).
  - Untuk akun lokal (non-Google), minta konfirmasi password.
  - Hapus / anonimkan data terkait: riwayat terjemahan, favorit, dan
    media yang tersimpan.
- Sediakan juga halaman web permintaan hapus akun (diwajibkan Google
  Play bila aplikasi dirilis ke Play Store).


================================================================
12. LOGGING & PRIVASI
================================================================
- Jangan pernah menulis ke log: header Authorization, password, OTP,
  reset token, dan isi media yang diunggah.
- Terapkan retention policy untuk media terjemahan yang diunggah
  (usul: hapus otomatis setelah N hari).

13. KESTABILAN LAYANAN
================================================================

  auto-restart bila proses jatuh).
- Siapkan 1 akun uji dengan data terisi (beberapa riwayat terjemahan
  dan favorit kamus) supaya pengujian tidak bergantung pada
  registrasi baru setiap kali.
